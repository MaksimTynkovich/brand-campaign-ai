# Overview

Краткое ТЗ MVP SaaS «TikTok Ads Generator для E-commerce»

Цель продукта:
Быстрое создание готовых рекламных креативов для TikTok (текст + видео) на основе описания продукта и изображений, в формате UGC, пригодных для запуска без доработки.

Целевая аудитория:
E-commerce бренды и маркетологи, запускающие TikTok Ads.

Функционал MVP:
	1.	Ввод данных о продукте:
	•	Название, краткое описание
	•	1–3 изображения
	•	Целевая аудитория, язык, рекламный угол
	2.	Генерация рекламного текста через GPT:
	•	Hook (3–5 вариантов)
	•	Видео-сценарий (10–15 сек, структура: Hook → Проблема → Решение → CTA)
	•	Caption + CTA
	3.	Генерация видео через n8n API:
	•	Использует загруженные изображения, сценарий и субтитры
	•	Формат 9:16, UGC-style, длительность 10–15 секунд
	4.	Просмотр и скачивание результата:
	•	Видео (MP4)
	•	Сценарий / текст (TXT / JSON)
	5.	Асинхронная обработка с очередью задач

Технологический стек:
	•	Backend: Laravel
	•	Frontend: React
	•	AI: GPT (текст)
	•	Видео и картинки: n8n API

Ограничения MVP:
	•	Только TikTok Ads
	•	Один продукт за генерацию
	•	Без аналитики, A/B тестов, интеграции с Ads Manager

KPI MVP:
	•	Время генерации видео < 2 минуты
	•	≥30% скачиваний сгенерированного креатива
	•	≥8–12% пользователей конвертируются на платный план

Используем tailwind CSS


# 🧱 1. Database Naming & Structure

## 📦 1.1. Имена таблиц

- Всегда **snake_case**
- Всегда **множественное число**
- Одна таблица — одна сущность

**Примеры:**

`users`, `orders`, `order_items`, `product_categories`

---

## 🔑 1.2. Первичный ключ

- Имя: `id`
- Тип: `BIGINT UNSIGNED`

---

## 🔗 1.3. Внешние ключи

- Формат: `singular_id`

**Примеры:**

`user_id`, `product_id`, `operator_id`

---

## 🔀 1.4. Связующие таблицы (pivot)

### **Использовать классические имена когда:**

- Простые отношения M:M
- Название `table1_table2` очевидно
- Отношение прямолинейное

**Примеры:**

`user_roles`, `user_pharmacies`

### **Использовать семантические имена когда:**

- Связь имеет важную бизнес-логику
- Название `table1_table2` неочевидно
- Нужна максимальная ясность

**Примеры:**
`favorites`,  `subscriptions`
**Если оба варианта не подходят, нужно выбирать семантическое имя + уточняющий суффикс**

**Примеры:**
`favorites_pharmacies`,  `favorites_products`

---

## 🕒 1.5. Timestamp-поля

- `created_at`
- `updated_at`
- `deleted_at` (soft delete)

---

## 📄 1.6. Enum’ы и статусы

- Поле: `status`
- Значения: **snake_case**

**Пример:**

`status = 'pending' | 'processing' | 'completed' | 'cancelled'`

---

## 🧩 1.7. JSON-поля

Имя должно отражать смысл:

`meta`, `payload`, `extra`, `settings`, `options`

# 🧱 3. Laravel Migration Style

## ✏️ 3.1. Одна миграция — одна ответственность

Плохой пример: добавить поле + создать таблицу

Хороший пример: **только одно действие**

---

## 📦 3.2. Формат именования миграций

- Laravel timestamp + snake_case:
    
    `2025_11_19_120532_create_orders_table.php`
    
- Название должно описывать действие:
    
    `create_orders_table`, `add_status_to_orders_table`, `rename_amount_to_total_in_payments_table`
    

---

## 🔗 3.3. Используем `foreignId()`

```php
$table->foreignId('user_id')->constrained();
```

---

## 🧹 3.4. rollback в down()

- Всегда писать, не оставлять пустым

---

## 🧱 3.5. Стандарты типов

| --- | --- |
| ID | bigIncrements |
| FK | foreignId |
| Длинный текст | text |
| JSON | json |
| Флаги | boolean |

# 🧱 5. Code Style & Architecture

## 🧱 5.1. Общие стандарты

- Следуем **PSR-12**
- Отступы — 4 пробела
- Максимальная длина строки — 120 символов
- Одна пустая строка между методами/классами
- Строгая типизация
- Не оставляем мёртвый код

---

## 🔤 5.2. Именование

| Тип | Формат | Пример |
| --- | --- | --- |
| Методы / переменные | camelCase | `getUserOrders()` |
| Классы / модели / сервисы | PascalCase | `OrderController` |
| Константы | UPPER_CASE | `DEFAULT_LIMIT` |
| Маршруты | kebab-case | `/user-profile/update-password` |

---

## 🧱 5.3. Архитектура Laravel

### Принцип

> Контроллеры тонкие → логика в сервисах/экшенах → валидация через FormRequest → отображение через Resources
> 

### Слои

- **Controllers** — только вызовы сервисов
- **Services / Actions** — бизнес-логика
- **FormRequest** — валидация и авторизация
- **Repositories / Query Objects** — сложные запросы
- **Resources** — API ответы

---

## 🎛 5.4. Контроллеры

- Один метод ≤ 20–30 строк
- Файл контроллера ≤ 100 строк
- Бизнес-логика — только в сервисах
- Используем FormRequest
- API через Resources

**Пример:**

```php
public function store(UserStoreRequest $request): JsonResponse
{
    $user = $this->userService->create($request->validated());
    return response()->json(new UserResource($user), 201);
}
```

---

## 📝 5.5. Валидация

- Всегда через **FormRequest**
- Не внутри контроллера
- Не использовать `Validator::make()` в контроллере

---

## 🗂 5.6. Модели (Eloquent)

### Можно

- Связи
- Касты
- Accessors / Mutators
- Query Scopes

### Нельзя

- Назвать связь по имени внешнего ключа
- Сложные вычисления
- Бизнес-логику
- API-запросы

```php
protected $casts = [
    'is_active' => 'boolean',
    'payload' => 'array',
];
```

---

## ⚙ 5.7. Services / Actions

- Один класс = одно действие
- Ясные названия: `CreateOrderAction`
- Зависимости через конструктор
- Методы строго типизированы

---

## 📚 5.8. Репозитории и Query Objects

- Использовать при множестве фильтров или сложных запросах
- Только работа с данными
- Мягкий, необязательный слой
- Названия: `OrderRepository`, `UserQuery`

---

## 🛢 5.9. Работа с БД

- Предпочтительно Eloquent
- Query Builder при необходимости
- Транзакции через `DB::transaction(fn() => …)`
- N+1 строго запрещён
- Миграции — всегда обратимые

---

## 🔌 5.10. API стандартизация

**Успех:**

```json
{
  "data": {},
  "meta": {}
}
```

**Ошибка:**

```json
{
  "error": {
    "message": "Not Found",
    "code": 404,
    "details": []
  }
}
```

- Используем только Resources
- Ошибки через централизованный Handler

- Используем фабрики

```php
 */

    // логика создания пользователя
}
```
